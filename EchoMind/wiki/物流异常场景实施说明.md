# 物流异常案件处理实施说明

## 阶段 0 现状盘点

现有链路：`POST /chat` 先鉴权和获取会话锁，读取 Redis 消息与 state，意图识别后构造 Request，AgentOrchestrator 合并实体和选择角色，执行有限轮工具调用，最后 commit_turn 原子保存消息、state、回执与 trace。
复用 IntentRecognizer、AgentProfile、路由表、BaseAgent 的统计和故障封装、SkillManager、知识库导入、Redis state、请求轨迹及幂等回执。原有物流意图只有一般咨询，没有订单核验、物流事实查询、案件存储或真实建单。
新增 core/logistics.py 的领域服务、SQLite 案件/模拟工单持久化、LogisticsAgent、三类异常意图、配置样例和演示规则。原 General、Technical、Billing、Escalation 保持原有分工。前端为独立工程，本次范围是 Python 后端。

## 阶段 1 场景与验收边界

首版覆盖疑似丢件 logistics_lost、签收争议 logistics_dispute、破损错发 logistics_damaged。正常查物流仍按原路径，不自动退款、赔偿、改址或认定责任。
缺少单号时追问；身份不符或订单运单不匹配时停止；查询失败和签收事实冲突时保存待人工核查状态；破损错发先要求材料；只有本轮明确“确认建单”才创建模拟工单。
所有外部事实来自 config/logistics/fixtures.json，规则来自 policies.json，返回显式 source=mock。演示数据快照是固定的，不能作为实时物流信息。人工处理状态不代表已通知真人客服。

## 阶段 2 案件和状态

SQLite 默认 data/logistics/cases.sqlite3，可用 ECHOMIND_LOGISTICS_DB 覆盖。Docker 已挂载 data/logistics。cases 记录用户、会话、问题类型、订单/运单、证据声明、核验事实、规则版本和事件；tickets 以 case_id 为唯一键保存工单。
状态为 awaiting_info → verifying → awaiting_evidence / awaiting_confirmation / manual_review → ticket_created。失败核验可再次进入 verifying；ticket_created 终态返回原工单。每次流转追加请求 ID 和工具名；最多保留最近 100 条事件。
通过 BEGIN IMMEDIATE 串行化并发更新，案件与工单在同一事务提交。SQLite 是首版单机持久化方案，不是多节点高并发数据库方案。Redis 会话 state 只保存案件指针和当前状态，案件事实以 SQLite 为准。换订单、运单、问题类型或明确新任务创建新案件。

## 阶段 3 工具与规则

query_order 校验当前 user_id 的演示订单归属；query_logistics 返回轨迹、更新时间或模拟超时；lookup_logistics_policy 返回确定性规则；create_logistics_case 在本地事务中幂等建单。规则属于演示规则，不是承运商真实政策。
工具不接收模型指定的用户身份或案件状态。破损材料只记录用户已提交的声明，没有文件上传、文件存储或视觉审核。查询超时用 fault=query_timeout 模拟。由于模拟工单与案件同库事务提交，不存在远程建单结果未知窗口；接真实后端前必须新增业务幂等键与按键查询接口。

## 阶段 4 编排接入

IntentCategory、模板、Pattern、实体提取和 _INTENT_ROUTING/_domain_scores 已增加对应类型和角色。编排器对明确异常表达作规则识别，并只对单号、提交材料、确认建单、继续/重试等短回复接续已有案件，避免其他问题误续接。CRITICAL 和明确转人工保持原升级优先级。
LogisticsAgent 复用 BaseAgent 角色契约、统计、AgentResponse 和轨迹接口，但案件的工具顺序与状态由确定性服务驱动，不交给模型自由决策。这样能防止跳过核验或确认；当前节点不额外调用 LLM，也不宣称新增了并行多 Agent 协作。政策使用本地版本化规则，RAG 资料用于通用知识检索，不决定写操作权限。
Skill 位于 skills/logistics_support/SKILL.md，说明业务边界。知识文档 config/logistics/knowledge.json 按项目原有 development + ECHOMIND_SEED_DEMO_DOCS 开关在 KnowledgeBase 初始化时幂等导入；production 不自动导入，可经 /knowledge/upload 上传该 JSON。本次环境没有运行中的 Redis/Chroma/Docker，未执行真实知识库导入和 HTTP 联调。
Trace 包含 query_order、query_logistics、lookup_logistics_policy、create_logistics_case 和案件转换事件，同一请求 ID 可关联；本地案件事件可用于重启后核查。确认建单前调用现有 before_unsafe_tool 回执保护，避免进程故障后自动重放不明结果。

## 本地演示

准备原项目模型配置、Redis 和 ChromaDB，按原 README 启动后端。development 下请求 user_id 使用 demo-user，生产鉴权开启时 Token 必须映射至同一用户。

1. POST /chat：user_id=demo-user，message=包裹疑似丢件，订单号 DEMO1001；保存返回 conv_id。
2. 同 conv_id 发“确认建单”，使用新的 client_request_id；返回 MOCK- 开头的模拟工单编号。
3. 同案件再次确认，返回原工单编号，不重复建单。
4. 新 conv_id 测试“显示签收但没收到，订单号 DEMO1002”。
5. 新 conv_id 测试“包裹破损，订单号 DEMO1003”，补充“已上传外包装、面单和破损照片”，再“确认建单”。
6. DEMO1004 模拟物流查询超时；非 demo-user 不能查询这些订单；DEMO1001 搭配运单 MOCK1002 会拒绝。

示例请求：
```json
{"user_id":"demo-user","message":"包裹疑似丢件，订单号 DEMO1001","client_request_id":"logistics-demo-1"}
```
后续每个新轮次使用新的 client_request_id；网络重试才复用原 ID。
