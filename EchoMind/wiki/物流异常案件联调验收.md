# EchoMind 物流异常案件联调验收

本次使用真实 DeepSeek 调用和本地 HTTP 接口，对模拟物流、SQLite 案件和工单、Redis 会话状态及 ChromaDB 进行联调。发现并修复一处转人工路由问题，修复后的 HTTP 与重启检查全部通过。

## 结果

| 验证范围 | 结果 |
|---|---|
| HTTP 业务与轨迹断言 | 34 / 34 通过 |
| 重启恢复断言 | 9 / 9 通过 |
| 物流单元、原 Agent 编排、意图识别回归 | 36 项通过 |
| 最终容器状态 | 后端、ChromaDB、Redis、Nginx、Prometheus 全部 healthy |

断言数包含业务状态与对应请求轨迹，不能解释为 43 个独立业务场景或模型准确率。

## 检查内容

1. 疑似丢件先核验并等待用户确认；确认后仅创建一个模拟工单。
2. 同一 client_request_id 返回原 request_id 和回执；新的确认请求也不重复创建工单。
3. 签收争议按规则建单，不认定责任；用户称已签收而轨迹未签收时，进入 manual_review 并标记升级。
4. 破损错发先进入 awaiting_evidence；用户直接确认不能建单；声明已提供材料后进入 awaiting_confirmation，再经确认创建工单。
5. DEMO1004 查询超时时保存案件并转人工，不建单、不伪造查询成功。
6. 非所属 user_id 查询被拒绝；订单和运单不匹配时停止，修正运单后可接续。
7. 同一会话换订单后产生独立案件，不沿用旧工单。
8. 每个物流请求都能按 request_id 查到工具轨迹和案件转换事件。
9. 重启 Redis 并重建 ChromaDB、后端容器后，原工单编号不变、不重建，历史轨迹和原客户端请求回执保留。
10. 重启前处于待举证状态的案件，重启后能通过短回复接续并完成确认建单；知识库仍为 9 个片段，没有重复导入。

## 修复的问题

输入“包裹破损，订单号 DEMO1003，转人工”时，模型可能返回物流意图。旧编排逻辑只阻止规则覆盖模型结果，没有主动把明确人工请求改成 handoff，导致仍进入物流节点。
现已在 agents/agent_orchestrator.py 中把明确人工请求设为 HUMAN_HANDOFF，并移除“不要转人工”等常见否定表达后再判断。新增两条回归用例，分别验证模型误分为物流时仍优先转人工，以及否定表达不触发该强制规则。新镜像已部署并经 HTTP 复测。

## 证据与边界

完整请求、回复、工具轨迹和断言结果保存在同目录 EchoMind物流案件验收证据.json。验收创建了独立的合成测试会话和 MOCK 工单，已保留以便核查；没有删除已有数据。

所有订单、物流轨迹和工单仍为模拟。举证检查只验证“用户声明已提交材料”，未验证真实上传文件或图片内容。当前是 development 模式，按 user_id 的归属拒绝不能替代生产 Token 身份鉴权测试；真实承运商 API、生产授权、性能负载和完整业务评测未包含在本次验收中。
