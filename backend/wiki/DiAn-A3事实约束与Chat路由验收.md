# A3 事实约束与 Chat 路由验收

本轮承接[业务回答链路验收](DiAn-A3业务回答链路验收.md)，处理“已签收”被解释成实际收件的问题，并将候选放入真实 /chat 路由、角色和汇总节点中观察。

## 修改与实验范围

共享角色提示明确区分系统状态、用户陈述和已核实事实，签收记录不直接证明本人收件。汇总节点也保留该约束，防止组合回复重写时丢失条件。

HTTP 回放同时暴露出账单角色的政策咨询偏差。旧 Billing Skill 要求优先收集订单和支付信息，导致“退款审核多久”无法获得语料已有的回答。本轮在共享提示、Billing 输入契约和该 Skill 中明确，一般政策先检索并说明已有规则，具体交易核验再收集必要信息。

调用实际 ASGI /chat 端点，使用真实模型完成意图识别、角色工具选择及汇总，加载现有四类 Skills。八条请求各使用独立会话。环境沿用已有隔离实验方式，Redis 为 fakeredis 协议模拟器，画像与情景记忆返回空值，物流业务库为临时 SQLite，知识工具为九段业务资料的 BM25 评测适配器。

本轮验证范围包括 API 处理、路由、角色组合、回执写入与工具轨迹。真实 Redis、生产启动、实际承运商和完整向量 RAG 链路需要对应环境验证。

## 观察结果

| 场景 | 基线观察 | 最终候选观察 |
|---|---|---|
| 列出订单状态 | General 列举六种状态 | 仍列出六种状态，当前输出未把签收解释为本人实际收件 |
| 签收规则、事实矛盾、状态解释三题 | 意图被识别为签收争议，进入 Logistics 收集订单号 | 同一分流现象持续存在，仍未直接回答规则问题 |
| 退款申请审核多久 | Billing 未检索，称需订单信息才能确定时长 | Billing 检索并给出审核 1–3、通过后到账 5–7 个工作日 |
| 401 加退款周期 | Technical 与 Billing 并行，汇总缺少已知周期 | 同样执行两个角色和汇总，最终保留 1–3 工作日审核周期 |
| 退款是否已经通过 | 无真实结果，索取订单及支付信息 | 仍无真实结果，仍索取目前不能用于实时查询的字段 |
| 发货后改地址 | 说明资料只规定发货前 | 保留该条件，发货后是否可改需另行核验 |

组合请求的响应记录 Technical 为主角色、Billing 为辅助角色，模型调用记录存在真实 composer 阶段。本轮证明了组合链路在该样本上的执行及已有政策信息的保留。

由于三条签收语义问题被路由到确定性案件节点，额外通过现有 GeneralAgent.handle 检查了三条表述，分别要求解释状态、判断记录是否足以证明收件、处理系统与用户陈述冲突。这三条绕过路由，单独记录。最终三条回复均明确签收记录不能证明本人实际收件，其中第一条同时引用《订单查询》和《签收争议演示规则》。

这种局部观察支持保留事实约束修改。HTTP 的三个签收咨询仍有分流缺口，独立检查的正确回复不能作为它们已通过的依据。

## 下一步

按照当前优化方案，下一步优先补齐已实际复现的两项用户体验问题。

1. 区分物流规则咨询和具体订单核查请求。先固定少量相近表述，在同一请求入口观察；规则咨询应能说明依据，需要处理具体订单时再进入既有案件流程。物流确认建单规则继续作为写操作裁决。
2. 对没有实时查询能力的请求，只索取能推动当前处理的字段。退款状态问题应引导用户到具备权限的渠道核实，避免无用收集。政策周期咨询保留本轮已经检索到的答案。

本轮交付保持在事实约束、现有角色规范和集成验证范围内。真实只读物流接入仍需要授权账户、供应商接口契约与可查询的运单。

## 复现

在 backend 目录配置实际模型并安装现有开发与评测依赖后执行。

```powershell
python -m evaluation.replay_chat_evidence --output data/rag-a3/chat-evidence.json
python -m pytest -q tests/test_agent_orchestrator.py
```

[完整请求、回复、角色与模型调用记录](../evaluation/chat_evidence_replay.json)保留三个版本和直接 General 检查。评测适配器的 BM25 方法名沿用共享知识工具的接口，实际运行直接 BM25 检索。
