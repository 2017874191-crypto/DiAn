# A3 任务目标与能力路由验收

本轮承接[事实约束与 Chat 路由验收](DiAn-A3事实约束与Chat路由验收.md)，实现业务主题之外的任务目标识别，并由实际工具能力决定实时状态查询能否继续。没有增加模型调用阶段，任务目标与原意图在同一次请求中返回。

## 实现

`IntentResult.task_goal`、编排请求和 /chat 响应增加可选字段，取值如下。

| 目标 | 含义 | 执行路径 |
|---|---|---|
| policy_question | 规则、含义、费用、时效与一般排障 | 物流异常主题可转 General 知识回答，其他主题继续现有角色路由 |
| status_lookup | 查询具体订单、物流或退款实时状态 | 检查所选角色的查询工具能力，缺少工具时直接说明查询渠道 |
| case_action | 明确申请或接续案件 | 进入既有案件核验与用户确认流程 |
| uncertain | 期望处理方式尚不明确 | 新会话先澄清目标，已明确的复合子问题继续分角色处理 |

主题分类保留原有三路逻辑，任务目标取自同一次模型识别。有效目标但模型置信度不足时保留不确定。旧模型输出或旧调用方没有字段时值为 None，继续兼容原流程。纯规则模式和模型失败路径仍沿用既有回退，当前任务目标优化适用于返回目标字段的模型路径。

规则咨询与状态查询不会仅因文本命中“签收但没收到”等异常表达而被强制改成案件。已有案件中的补单号、补材料、确认与重试仍接续原案件，确认文句是否有效继续由现有领域规则判断。任务目标自身不授予建单权限。

`AgentToolSpec.capabilities` 新增可选元数据。受信任的工具注册代码可声明 `status_lookup`，其余工具默认没有该能力。编排器检查当前角色可见的工具，缺少查询能力时直接返回能力说明，停止后续字段收集。此时只使用已有意图调用，无额外回答模型调用。

Billing 输入契约中，政策咨询与缺少工具的状态查询不产生固定订单/支付缺失字段。确有查询工具时，缺失字段来自该工具 JSON Schema 的 required，并扣除已经提供的实体。参数及主体授权仍由实际工具与业务接口核验，能力标签只是路由依据。

## 针对性回归

新增六项回归覆盖现有意图调用同时解析目标与旧格式兼容、规则咨询避开物流案件、无工具与未知目标停止字段收集、声明查询能力后实际调用工具、案件确认接续、复合问题保留原角色组合。

带查询能力的协议测试使用仅需要 order_id 的工具，核对字段清单没有多收支付金额，并执行该测试工具取回结果。无真实供应商接口参与。

在代码 56cac12 上，原相关测试与物流案件、澄清及 API 回归共 98 项通过。随后 c2d250e 补齐工具 Schema 驱动的字段清单，48 项直接相关测试再次通过。存在一条原有依赖警告。[56cac12 自动检查](https://github.com/2017874191-crypto/DiAn/actions/runs/44486286183)已通过。

## 真实模型回放

复用已有 ASGI /chat 回放器，使用真实模型、现有 Skills、九片段 BM25 评测适配器、Redis 协议模拟器及临时 SQLite。最终代码 56cac12 覆盖 12 个 HTTP 请求和三条直接 General 检查。

| 请求类型 | 最终观察 |
|---|---|
| 三条签收规则/状态含义咨询 | 目标均为 policy_question，General 回答，未建立案件 |
| 退款实时审核结果 | status_lookup，保留 Billing 主题，直接说明没有查询能力 |
| 指定订单实时物流位置 | status_lookup，直接说明没有查询能力 |
| 明确申请签收争议核查 | case_action，进入 Logistics，使用归属已知的演示订单核验后停在 awaiting_confirmation |
| “我没收到，现在怎么办” | uncertain，询问用户希望了解规则、查询状态还是申请处理 |
| 明确暂不申请的规则咨询 | policy_question，解释知识规则，未进入案件 |
| 401 与退款周期复合请求 | policy_question，Technical、Billing 与 composer 均执行，保留退款周期 |

最终 12 条目标与本轮开发预期一致，全部 HTTP 200 且执行状态成功，未创建工单。两个无查询能力请求的调用记录都只有一次 intent，回答由确定性能力说明返回。已有案件误标后的确认建单在回归中另行验证，最终仍只有一张模拟工单。

第一版开发回放为 11 条 HTTP 请求、三条直接检查，出现两处目标偏差，复合问题被标 uncertain，以及含糊的“怎么办”被标 case_action。修改提示说明和复合问题处理后，最终回放为 12 条 HTTP 请求、三条直接检查。两轮分别使用 24、33 次模型调用，均无模型错误，首次结果保留。最终有 12 次 intent 调用，对应 12 条 HTTP 请求。

这批输入用于发现问题和调整实现，属于已曝光开发样本。12 条匹配不能推导独立准确率，语义观察来源为 Codex 模型辅助检查。现有规则咨询回复仍会提供一般建议，需要继续在真实业务语料中检查引用和适用性。

## 决策与复现

保留任务目标与能力路由。本轮用既有调用增加结构化目标，并将缺少查询工具时的行为落到代码，减少无用字段收集。当前不据此接入真实订单、支付或承运商操作。下一阶段沿优化方案准备真实只读接口的授权与契约，并用新的相近表述检查目标划分，继续使用已有领域确认和结果核对边界。

在 backend 目录执行。

```powershell
python -m evaluation.replay_chat_evidence --output data/rag-a3/chat-task-goals.json
python -m pytest -q tests/test_agent_orchestrator.py tests/test_intent_recognizer.py tests/test_chat_reliability.py
```
