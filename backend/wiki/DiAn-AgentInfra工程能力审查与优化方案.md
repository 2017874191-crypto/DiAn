# DiAn：Agent Infra 面试项目工程能力审查与优化方案

审查日期：2026-11-11

代码基线：59bca6bb258551885ff5248a046ba78e88db4c5f（v0.1.0-interview）

适用方向：Agent 应用运行时、工具执行与治理、可靠性、评测基础设施；不以 GPU 推理服务、模型训练或集群调度为主。

文档性质：现状审查与待实施方案。本文中的目标、接口、表结构和验收指标均不是已交付能力。

## 1. 结论与项目定位

DiAn 已具备“有可靠性意识的 Agent 业务应用”基础，可以展示确定性状态机、模拟交易幂等、工具约束和案件级评测。若作为 Agent Infra 岗位的主项目，当前最缺少的是一条能经受进程崩溃、依赖故障和并发压力的通用执行链路：任务可追踪、执行可恢复、副作用可核对、资源可限制、版本可复现。

不能把现状简单评价为“全是 demo”。已有的会话互斥、Redis 原子回执、SQLite 案件与模拟工单同事务、JSON Schema 校验、工具熔断及测试均有价值。但这些机制的保证范围主要是单次请求、单个进程或固定模拟世界，尚未形成跨进程、跨服务的完整保证。

建议把下一版定位为：

> 基于物流案件验证的可恢复 Agent 执行服务：模型负责理解与建议，领域策略负责授权与状态转换，运行时负责预算、执行、恢复和追踪。

这里的“运行时”先只支持项目实际需要的固定步骤，不预先实现通用 DAG 编辑器、自治规划平台或任意代码执行沙箱。

## 3. 从第一性原理确定最小需求

Agent Infra 的对象不是“几种 Agent 类”，而是一个包含不确定模型输出、可失败外部依赖和不可随意重复副作用的执行过程。

必须建立以下不变量：

| 编号 | 不变量 | 最小工程落点 |
| --- | --- | --- |
| I1 | 模型、文档、工具描述不能自行授予写权限 | 服务端身份、工具策略、领域确认凭证 |
| I2 | 每个已接受任务有持久身份和可查询结果 | Run、Step、Operation 及状态 API |
| I3 | 未知结果不能被当成失败后随意重做，也不能永远悬置 | 持久化未知态、按幂等键查询、对账和人工核验 |
| I4 | 重试可以发生多次，业务副作用在约定范围内至多一次 | 稳定业务键、数据库唯一约束、Provider 幂等/结果查询 |
| I5 | 旧执行者不能在新执行者接管后覆盖结果 | 写端版本比较或 fencing；单纯租约续期不足 |
| I6 | 被接受的并发、模型调用和等待都有上界 | admission、队列、信号量、总 deadline 与预算 |
| I7 | 一次运行的策略、提示词、工具与模型配置可追溯 | 不可变配置快照及 hash |
| I8 | 实验比较在相同任务与故障条件下成立 | 冻结数据、实验元数据、配对报告及失败保留 |
| I9 | 缓存、向量库和摘要损坏不能改变授权事实 | 事务库保存业务事实，派生数据可重建 |
| I10 | 故障诊断可定位步骤且不暴露凭据或无关用户数据 | 结构化事件、span、脱敏、保留策略 |

“Exactly once”应限定为有去重协议支持的业务效果，不能承诺网络请求只发送一次。下游既无幂等键又无结果查询时，不能通过本地重试构造通用的恰好一次保证。

## 4. 逐模块对抗性审查与优化

### G01：物流同步事务会阻塞事件循环，Provider 边界仍与 SQLite 耦合

**证据**：[LogisticsAgent._call_llm][E01] 直接调用 service.process；[事务主体][E02] 在 BEGIN IMMEDIATE 后执行订单查询、物流查询和工单创建，SQLite busy_timeout 为 5 秒。[Provider 接口][E03] 的 create_ticket(db, case_id, idempotency_key) 暴露数据库连接；其顶部“worker thread”注释与当前调用路径不一致。

**对抗场景**：订单服务慢、SQLite 被另一进程占用、将 MockProvider 直接替换成同步 HTTP。其他请求、心跳和续租会被一起阻塞。T1 已验证基本调度问题。

**最小优化**：先定义请求 deadline 和执行归属，再把网络读取移出写事务，采用有界异步 I/O；持久写入由明确的执行单元承担。事务只做检查版本和状态提交；外部写操作走 Operation 记录和幂等协议。接口返回类型化结果，TicketProvider 不接收数据库连接。

**取舍**：不能只包一层 asyncio.to_thread 就宣称解决。取消等待不会确保运行中的同步操作停止，必须保留结果归属和核对路径。Python 的事件循环采用协作调度；阻塞 I/O 与异步超时需要一起设计。[Python 文档](https://docs.python.org/3.12/library/asyncio-task.html)

**验收**：独立 Provider 延迟 2 秒时健康端点仍可响应；写锁竞争不会拖住全局事件循环；取消后若外部已成功，结果最终归档且不再建单。具体负载目标见第 8 节。

### G02：回执阻止了盲重试，但未知结果没有恢复出口

**证据**：[chat 调用前标记][E04] 将 tool_outcome_unknown 写入 Redis，retryable=false；同 ID 再请求会直接返回该标记。[commit_turn][E05] 回执 TTL 为 86400 秒。物流写入 SQLite 与最终 Redis 回执不在同一事务。

**对抗场景**：未知标记已提交但还没发起调用时崩溃；外部成功后响应丢失；SQLite 已提交而 Redis 回执写失败。当前前两类都可能留在未知标记，缺少统一核对流程。已有测试证明“不会重放”，没有证明“最终能收敛”。

**最小优化**：持久化 Operation，区分 prepared、in_flight、succeeded、failed、outcome_unknown。执行前提交操作意图，调用使用稳定幂等键；重启后先查下游结果，确认不存在且契约允许才重试。SQLite 本地模拟可直接查询 tickets 进行核对，独立模拟 HTTP 服务用于验证跨服务窗口。

**幂等范围**：请求 ID 负责同请求去重，operation_id 负责同操作去重，业务键负责跨会话重复申请。T3 证明当前只覆盖前两者中的部分范围。推荐业务键为“身份/租户＋订单＋问题类型＋活动案件代次”，结案后有明确的新一轮申请规则，不能永久封死合法新案件。

**验收**：在“记录意图前后、外部成功后、本地结果提交前后”分别终止 worker，恢复后同操作最终最多一个外部工单；真实不确定状态可查询、告警并可人工核验。不得自动把超时改写为失败或成功。

### G03：持久案件依赖短期会话指针，恢复保证不完整

**证据**：[会话状态][E05] 与历史同为一天 TTL；[/logistics/case][E06] 先读 Redis 指针再查 SQLite，不按用户与会话从持久库找回案件。T2 已复现“案件存在、会话指针为空”。

**最小优化**：事务库维护会话与案件关联、活动案件索引；Redis 只缓存。查询时按认证身份与会话查持久关系，更新缓存但不重新授权。会话过期策略与案件保留期限分别定义。

**取舍**：不需要为了修这个问题立刻上 PostgreSQL；先增加 Repository 与迁移。若要验证两 worker 并发接管和任务抢占，则采用一个 PostgreSQL 共享事务源更直接。

**验收**：删除/过期派生 Redis 状态后能找回原案件；未授权用户仍无法读取；换订单、新会话与已结案后的新问题按明确规则处理；备份恢复后关联可重建。

### G04：缺少可恢复的任务执行模型

**证据**：[主请求][E04] 在 HTTP 生命周期内完成；[Agent 工具循环][E07] 最多三轮，没有 Step 持久化；[评测任务][E08] 用字典和 create_task，服务重启后查询 404。三轮限制有价值，但不是持久化运行时。

**最小优化**：引入最小 RunStore，先支持固定步骤：识别、核验、等待确认、写工单、结果核对。API 接受后返回 run_id；worker 执行、持久化检查点；GET 查询状态；POST cancel 记录取消请求。先用数据库任务表领取任务，避免立即再增加消息队列。

**状态语义**：waiting_input 不占 worker；同一案件不同输入生成不同 run，以 case_id 相连。已派发外部写操作后取消，只能停止后续步骤并核对既有结果；不能承诺撤销已完成操作。对账未结束的任务不能标记为“已取消且无副作用”。

**验收**：worker 崩溃后可由另一 worker 接管；已完成外部步骤不重复；已过期执行者的结果被写端拒绝；新输入和旧输入的顺序有版本校验。持久化运行语义可参考 [Temporal Workflow Execution](https://docs.temporal.io/workflow-execution)，本阶段不要求引入该平台。

### G05：会话锁不等于资源调度，应用缺少有界模型接入

**证据**：[KeyedLocks/redis_lease][E09] 控制同会话互斥；[ProfileUpdater][E09] 与评测队列有上限；[Nginx 配置][E10] 已有 IP 限流和连接限制。但 /chat、/search 等直连 API 没有全局/身份级在途任务上限；单个共享 Agent 对象也不是一个受控 worker 槽位。

**对抗场景**：大量不同 conv_id 并发，单租户突发，在线会话与评测同时占模型额度，画像更新堆积。按会话串行无法约束总量；Nginx 的入口限速也不能约束一次请求派生的模型调用数。

**最小优化**：接入层限制待运行数量，超出返回 429 和 Retry-After；执行层设置全局、身份/租户和依赖级并发额度；任务携带绝对 deadline、最大工具调用次数、模型输出与调用预算。评测/画像使用低优先级独立额度。

**取舍**：本机先实现显式额度和有界队列，再通过负载测试决定是否需要复杂公平调度。跨进程额度不能用每进程 Semaphore 冒充全局额度。

**验收**：饱和负载下资源在预设上限内，拒绝数与接受数可解释；已接受任务不被静默丢弃；不同身份都有进展；排队时间计入总 deadline；取消释放额度。

### G06：租约、取消与真实写入之间缺少写端防护

**证据**：[redis_lease][E09] 续租失败时取消持有协程，是已有的正确防御；但业务提交没有携带单调递增执行代次或预期版本。同步阻塞、线程中的 handler 或已经发送的网络请求不受协程取消直接约束。

**风险推演**：worker A 暂停或网络分区，租约到期，B 接管；A 恢复后仍提交。尚未在本轮做真实跨进程故障实验，不能称为已复现的数据破坏。

**最小优化**：数据库领取任务时递增 lease_epoch；结果提交必须同时匹配当前 epoch、状态和版本。业务 CAS 与唯一约束决定是否能提交。外部系统不能验证 epoch 时，稳定幂等键和结果核对负责外部副作用，不能指望本地 fencing 自动保护远端。

Redis 官方讨论了租约有效期及 fencing 的必要性；当前实现是单 Redis 租约，不应称为已经实现 Redlock 或分布式一致性协议。[Redis 文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

**验收**：暂停 A、让 B 接管、恢复 A，旧 epoch 的状态写入被拒绝；远端同幂等键最多一个效果；没有把 Python 取消测试冒充进程暂停测试。

### G07：工具与 MCP 已可用，安全策略尚未形成统一契约

**证据**：[AgentToolSpec][E11] 的 retry_safe 默认 true；[MCP 注册][E12] 根据配置和远端 readOnlyHint 决定 retry_safe；本地 context.user_id 用于缓存范围，但 [_call_remote][E12] 只发送工具名与参数。角色工具白名单、输入 Schema、只读注册检查和限长均已存在，应保留。

**对抗场景**：新增有副作用工具忘记覆盖默认标记；远端误报只读；工具热更新改变 schema/行为；模型填入其他用户订单；不可信工具内容诱导执行高风险工具。

**最小优化**：
- 本地显式声明 read_only / idempotent_write / non_idempotent_write，未知默认拒绝自动重试。
- 服务端策略决定可见工具、参数权限、资源归属；远端 metadata 只能作为检查输入。
- 确认凭证绑定 user/tenant、case、action、参数摘要、策略版本和有效期；参数变化后重确认。
- 固定每次运行的工具目录 hash，校验返回结构；跨服务身份由可信凭据或受控代理传播，不能把用户身份作为模型可编辑参数。
- 对 stdio 工具只支持管理员登记的可信服务；若未来支持第三方可执行程序，再单独设计进程/容器隔离和网络范围。

MCP 规范明确要求：不可信服务的工具 annotations 不应直接视为可信事实。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

**验收**：恶意描述不能扩大工具权限；假只读元数据不能绕过本地写策略；错用户、错订单、过期确认和参数篡改均在工具调用前被拒绝；Schema 改动不会悄悄影响在途运行。

### G08：静态 Token 鉴权具备基础，多租户与知识隔离尚未成立

**证据**：[access.identity][E13] 提供生产 Token 配置检查和 user/admin 映射；chat 用认证身份覆盖请求 user_id。知识库使用单 collection，[search][E14] 无 tenant/ACL filter；[/search][E15] 未向查询链传身份，MCP 本地检索也使用公共知识库。

**判断**：对“所有用户共享公开客服政策”的单租户演示，这是可接受范围；不能由此声称支持企业私有文档多租户隔离。目前没有证据表明已导入真实跨租户私密数据。

**最小优化**：先定义 deployment mode：单租户公共知识库，或多租户私有知识库。选择后者才加 RequestContext(tenant_id, user_id, roles)、每次数据访问与缓存键的租户约束；租户由服务端凭证推导。静态 Token 可继续用于受控演示，真实部署再接可信身份服务和轮换。

**验收**：两个身份/租户使用相同文档 ID、订单号、会话号和查询文本，读写、缓存、轨迹均不串；匿名与普通用户无法调用管理接口；工具参数不能覆盖认证上下文。

### G09：模型调用有统计，但缺少预算、可控重试和全链路资源账户

**证据**：[create_message][E16] 记录逻辑 SDK 调用；[performance][E17] 明示不统计 SDK 内部重试，未报告 token 不估算。不同组件自行实例化 AsyncAnthropic、设置不同超时；工具三轮不限制每轮所有工具的总成本。

**最小优化**：共享 ModelGateway 与 RunBudget：使用剩余 deadline；区分请求级 deadline、连接/读取超时和阶段预算；显式配置 SDK 重试，避免多层重试放大；按 429/暂时故障与确定性参数错误分别处理。开始调用前预留预算，完成后结算，未知用量保留 unknown 标记。统计每个已接受案件及成功案件的消耗，覆盖失败与后台任务。

**取舍**：先一个生产兼容 Provider 加一个可控 stub，不必为面试接五家模型。没有冻结价格与账单校验时只报告调用/token，不制造人民币成本。

**验收**：连续 429、超时、空输出、截断与错误结构不会突破调用上限；失败和重试计入消耗；取消释放预留资源；预算耗尽有明确终态。

### G10：监控能显示结果，尚不足以追溯完整执行

**证据**：[Prometheus][E18] 有请求数、Agent/HTTP 耗时和成功率；[performance][E17] 有 ContextVar 阶段统计；[回执 trace][E05] 在 Redis 保留 7 天、最近索引 200 条；[redaction][E19] 过滤常见凭据。并非“没有监控”。

**缺口**：客户端请求 ID、内部 request_id、后续 run/step/operation 尚未统一关联；失败发生在回执前可能缺少完整轨迹；进程内统计和 histogram 不能直接视为多 worker 聚合。部分日志直接记录查询、消息片段、异常字符串，轨迹脱敏并不等于日志全面脱敏。

**最小优化**：先确定事件字段，再接 OpenTelemetry：run/step/tool/model span，携带 traceparent；execution event 持久化供恢复审计，span 用于诊断，二者职责不同。指标 label 只使用有限类别，run_id、订单号和用户 ID 留在受控日志/追踪中。默认不收集完整提示词/工具返回。

**建议 SLI**：接收与拒绝数、终态覆盖率、未知结果存量与年龄、重复副作用数、队列等待、实际模型调用、恢复耗时、分阶段 P95。部分回复、人工核查、HTTP 成功要分别计数。跨服务因果链与 span 关系参考 [OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)。

**验收**：从一个 run_id 能找出所有重试、失败、接管与外部操作；重启不丢关键审计；含测试凭据的输入不会出现在导出日志中；故障告警有可执行处理手册。

### G11：记忆和 RAG 的工程优化先于收益证明

**证据**：[记忆读取/压缩][E20] 使用用户过滤和 WATCH，后台更新有节流；压缩在 Redis 裁剪后调用 Chroma 归档，归档失败只日志记录。向量库仅存摘要及截断的原文片段，并非可靠原始事件存储。[RAG][E14] 有内容 hash，但分块先 upsert 后删除，不是跨实例原子索引切换；[缓存][E21] 的失效版本与 single-flight 均为进程内。

**对抗场景**：长期画像保存了不再正确的地址/偏好；跨会话摘要被误当成本次事实；Chroma 故障造成归档缺口；另一个 worker 继续命中旧文档缓存；注入文档指示越权调用工具。

**最小优化**：事务性业务状态与生成的记忆分离，记忆不授予权限；按 token 总预算裁剪上下文，保留字段来源/时间/版本。仅在“关闭长期记忆有可测损失”后保留画像；需要可靠归档时用 outbox 或可重建索引。私有知识增加 ACL；多实例时用显式索引 revision，并原子切换活动版本。

**取舍**：物流确定性主流程并不需要全套查询改写、重排和长期画像。先验证必要路径能否跳过这些依赖；不要把“三级记忆”本身当作必须保留的亮点。

**验收**：旧摘要不能覆盖新订单事实；重建索引不丢业务事实；文档更新后各 worker 的版本一致；关闭画像/情景召回后的质量、延迟和成本差异按第 7 节报告。

### G12：评测已有价值，但缺少足以支持架构决策的强证据

**证据**：[evaluate_turn][E22] 检查状态、issue、Agent、工具名称和工单数量，但不检查关键调用先后、成功结果和授权事件。T4 已复现断言缺口。回放报告不是持久执行日志。历史文档中部分“意图断言”表述也应对照代码区分：当前函数检查案件 issue，不直接检查独立 intent 字段。

[compare][E23] 校验 suite/split/variant 与案件集合，但 image_id 来自命令参数，dataset hash 来自比较时本地文件，不能证明三份运行报告确实来自同一镜像、数据、模型及策略。已有 fixture hash 检查是有效基础，但不是完整实验身份。

**最小优化**：
1. 必要动作的偏序、业务成功、确认发生在此前核验后、失败路径禁止写入，都成为独立断言；保留允许缓存/重试的显式规则，避免僵化要求全部轨迹逐字相同。
2. 报告生成时固化 commit、image digest、数据集/fixture/policy/prompt/tool hash、模型配置、依赖锁、运行环境、故障种子、时间与配置开关。
3. 比较器对身份不匹配和元数据缺失直接拒绝比较；不能把一个 CLI image_id 赋给所有历史报告。
4. 代码贡献加入 CI：单测、真实 Redis+事务库集成、故障/权限回归、前端构建。模型评测单独运行与留存脱敏产物。
5. 测试集人工金标和回答语义复核由真实复核者完成；自动检查器不能代替签名和裁决。

**验收**：T4 反例失败；混入不同版本报告被拒绝；提交若导致副作用门槛回归则 CI 红；统计中保留 503、超时、unsupported 和未运行案件，不从分母中静默删掉。

### G13：Skills、业务确认与配置版本没有一致的发布边界

**证据**：[SkillManager][E24] 热加载会替换当前列表，模型循环每轮生成系统提示；[物流规则][E02] 使用硬编码 RULE_VERSION，确认主要检查先前状态与版本字符串。无统一发布快照、参数摘要、审批事件和灰度回滚。

**最小优化**：ReleaseConfig 固化 prompt、skill、tool、policy、model 配置 hash；run 开始时固定配置。物流确认绑定展示方案和参数摘要，核验事实发生影响方案的变化时重新确认。策略版本由实际内容/发布元数据驱动，不能改规则内容却保留旧常量。

**验收**：运行途中热更新只影响新 run；旧确认不能批准新方案；回滚后新运行采用旧配置且报告可追溯。增加配置版本属于小型发布能力，不需要建设独立配置平台。

### G14：本地交付可用，构建、恢复与“人工协同”尚有演示边界

**证据**：[Dockerfile][E25] 非 root、多阶段构建、预下载模型已具备，但生产构建消费 requirements.txt 而非完整传递依赖锁；基础镜像/tag、部分依赖为浮动版本，模型下载无内容 hash 校验。[Compose][E26] 是单应用容器与本地持久卷，不能据此称为高可用；[/health][E27] 主要检查编排器对象，不检查运行后的依赖故障。仓库基线未包含 .github 工作流。

物流 manual_review、EscalationAgent 和 evidence_declared 是状态、回复/摘要与声明记录，没有真实审核员领取、操作授权、回写及证据对象存储。它们适合作为演示，不是已接入的工单协同系统。

**最小优化**：统一 3.12 构建与测试环境，生产锁依赖、固定镜像及模型校验；数据库 schema migration、备份/恢复、回滚手册。拆分 liveness/readiness/degraded，只因关键执行依赖不可用而拒绝接入，不能让可选向量库故障不必要地停掉全部服务。人工协同在核心执行稳定后做一个真实审核 API；证据对象与声明分开。

**验收**：从空环境复现相同依赖；备份恢复能查询任务/操作；发布失败可回滚且 schema 兼容；依赖故障下 readiness 与实际可接受操作一致；未配置真实客服时不显示“已通知客服”。

## 5. 最小目标架构与高内聚、低耦合

建议新增能力按职责拆分，保留现有领域服务。不要把 1373 行编排器简单切成许多相互引用的文件，也不要一次性重写全部基线。

~~~mermaid
flowchart LR
    A[API：身份与接入限额] --> B[RunService：接受与查询任务]
    B --> D[(事务库：Run / Step / Operation / Case)]
    W[Worker：领取任务与恢复] --> D
    W --> R[Runtime：预算与步骤推进]
    R --> L[物流领域：规则与确认]
    R --> M[ModelGateway]
    R --> T[ToolExecutor：策略与结果核对]
    T --> P[Provider：订单 / 物流 / 工单]
    L --> D
    R --> O[结构化事件与追踪]
    T --> O
~~~

| 边界 | 负责 | 不承担 |
| --- | --- | --- |
| api/ | 认证、输入契约、接入限额、状态查询 | 工具重试和状态机内部细节 |
| runtime/ | Run/Step 生命周期、deadline、预算、取消与恢复 | 物流异常判定 |
| domains/logistics/ 或原 core/logistics | 案件状态、核验政策、确认条件 | HTTP SDK、缓存、模型重试 |
| tooling/ | 工具策略、Schema、操作身份、副作用协议 | 自动决定用户是否同意 |
| providers/ | 外部协议、超时、幂等与查询结果 | 案件状态机 |
| persistence/ | Repository、事务、迁移、领取与 CAS | 提示词内容与业务话术 |
| evaluation/ | 数据、断言、故障注入、比较与产物 | 偷改线上策略以提高分数 |
| observability/ | 事件、日志与指标导出 | 决定业务成功与交易回滚 |

以上是目标边界，目录名称可在实施时适配现有结构。先抽出一个稳定接口并通过测试，再迁移其调用方，避免机械拆文件。

### 5.1 建议的最小持久结构

| 实体 | 关键字段和约束 |
| --- | --- |
| runs | id、主体身份、case_id、client_request_id、input_hash、status、deadline、budget、config_hash；主体+请求 ID 唯一，同键异参拒绝 |
| steps | run_id、step_key、status、attempt、input/output 引用、版本；逻辑步骤身份稳定，恢复不是重新生成新步骤 |
| operations | operation_id、业务去重键、tool/version、参数摘要、confirmation_id、state、external_id、attempt、next_reconcile_at；稳定键唯一 |
| leases | run_id、owner、lease_epoch、lease_until；领取/续租/提交使用 CAS |
| cases | 认证主体、订单/异常、业务状态、version、active_generation、会话关联 |
| execution_events | run/step/operation、事件序号、时间、结果摘要、配置版本；追加写，设置保留策略 |

记录完整模型对话或巨型工具返回应有上限与脱敏；需要重放时保存必要的结构化输入/输出及引用，不将所有内容直接塞入事件表。

一开始可将待派发操作与其状态放在同一个事务库，避免“SQL 提交后再往 Redis 队列推送”的双写窗口。只有任务表压力成为实测瓶颈时才引入独立消息系统与 outbox。

## 6. 分阶段优化计划

以下工作量为单人熟悉代码后的初步估算，不含人工金标等待与真实系统对接时间。优先按验收门槛推进，不以日历到了就标为完成。

| 阶段 | 目标与范围 | 交付物 | 完成门槛 | 估算 |
| --- | --- | --- | --- | --- |
| M0：证据与边界 | 固化本文基线；补 T1–T4、报告身份、Schema/状态设计；建立最小 CI | ADR、失败回归、实验 manifest、CI | 旧功能保持通过，新增反例能暴露原问题，混版本比较失败 | 2–3 人日 |
| M1：持久化最小闭环 | Run/Step/Operation、持久会话关联、本地工单结果核对；隔离阻塞执行，明确取消语义 | 迁移、Repository、状态 API、恢复器 | 重启/过期回执后能查询原结果；未知结果不永久悬置 | 4–6 人日 |
| M2：真实故障边界 | 独立模拟 HTTP Provider、两 worker 接管、epoch/CAS、预算与接入限额 | 故障模拟器、集成测试、负载脚本 | 外部成功但丢响应等窗口无重复效果；过载受控 | 4–6 人日 |
| M3：治理与可解释性 | 工具策略、主体传播、确认凭证、固定配置、追踪与 SLI | 策略回归、trace 样例、告警手册、恢复演示 | 权限矩阵通过；从 run_id 可解释故障和副作用 | 3–5 人日 |
| M4：减法与候选版 | 多轮配对消融、人工语义复核、报告留存、冻结新版本 | 实验报告、保留/删除决策、面试演示脚本 | 每项保留复杂性有证据；未完成项明确标注 | 2–4 人日+人工等待 |

合理预计 15–24 人日完成上述受控范围。不要把多租户企业平台、真实赔付、通用代码沙箱一起计入这个估算。

**紧接着的第一批任务**：

1. 确定业务去重口径、运行终态与未知结果协议，用 ADR 固定决定。
2. 把四个探针转成正式回归；增加“成功建单后回执失败”的恢复测试。
3. 实现事务性 Operation 记录与持久案件查找；先用当前 SQLiteTicketProvider 跑通结果核对。
4. 再解耦 Provider 和同步事务，做独立 HTTP 故障服务。
5. 补两 worker 接管与有界执行；通过这些门槛后才扩大真实系统接入。

本轮仅形成分析与方案。M0–M4 中的代码、CI 和基础设施均待后续实施。

## 7. 消融实验：证明机制必要，而非证明方案复杂

### 7.1 历史结果应该如何解释

历史 P2：规则组 21/30、LLM+规则 30/30、完整组 29/30；完整组一次未定位服务失败。P3：物流向量开/关各 30/30。冻结版使用 full 且物流向量关闭，原始报告本轮已核对。

这些结果支持“LLM 能补充当前规则对委婉表达的覆盖”和“尚未观察到物流向量的独立收益”两个有限判断。它们不支持“完整方案生产准确率达到 100%”或“向量一定无用”。P2 的 rules_only 对未命中输入使用固定澄清，与完整客服能力不等价，应分别报告物流与非物流子集。

### 7.2 必须执行的实验矩阵

| 实验 | 对照与处理 | 主要假设 | 指标与决策 |
| --- | --- | --- | --- |
| A1 意图分支 | rules_only、llm_rules、full；另做只关闭物流向量 | 向量能在相同规则下增加正确案件处理 | 按场景族配对成功/失败、误建案、错建单、延迟与调用；无稳定增益时关闭该领域向量 |
| A2 长期记忆 | 当前记忆；仅近期消息+结构化案件；关闭画像；关闭情景召回 | 长期记忆改善必要的跨轮/跨会话任务 | 实体续接、事实冲突、旧信息污染、token、延迟；无收益则从物流关键链路移除 |
| A3 RAG 增强 | 单查询基础召回；+改写；+重排；完整链路 | 增强检索提高有依据的回答 | 有金标的 Recall@k/nDCG、引用正确性、回答语义、调用；仅对需要知识检索的样本统计 |
| A4 多 Agent 合成 | 单主 Agent；主+辅+合成 | 复合请求确实需要并行角色处理 | 意图覆盖、遗漏/冲突、语义质量、端到端耗时与总成本；纯物流固定流程不混入此比较 |
| A5 缓存与 single-flight | 无缓存；缓存；缓存+同键合并 | 重复负载下降低成本且不串身份/旧版本 | 固定重复率及冷热缓存，测实际调用、命中、陈旧结果与内存；零收益时简化 |
| A6 路由降权/熔断 | 固定策略；熔断；动态降权 | 故障时提高完成率或减少无效负载 | 固定故障序列、失败次数、恢复时间、误降级、质量；故障结束后验证恢复 |
| A7 持久恢复 | 仅最终回执；+操作记录/核对；+接管防护 | 机制覆盖对应崩溃窗口 | 各断点的丢任务、重复效果、未知态时长、恢复耗时；每项防护对应可复现反例 |
| A8 有界调度 | 无接入限额；全局限额；全局+主体配额 | 饱和时保持有界内存及主体公平 | 接受/拒绝/完成、队列等待、RSS、事件循环延迟、不同主体进展 |

A7/A8 中移除安全保护只在隔离故障实验中执行，不能对真实订单做在线消融。

### 7.3 实验纪律与删减规则

- 优先在 dev/专用故障集设计方案；冻结 test 只做最终一次候选评估。失败后可修复，但应声明测试集已被用于开发，新增盲测集，不能继续称未见过的测试集。
- 初期每组至少 5 次跨时段回放，组间交错顺序；按相同案件、相同故障种子配对。五次只是初筛，样本不足时标明不确定。
- 固定代码、模型标识、提示词/策略/工具 hash、数据划分、资源、缓存状态与依赖版本；供应商不能固定实际模型快照时记录这一限制。
- 按案件而非独立轮次计算成功率；耗时按所有尝试和成功尝试分别报告；失败请求不完整 token 记未知，不能当零。
- 报告配对差异和置信区间；相关场景族可按 family 分组重采样，避免把同模板重复当独立证据。保留全部失败，单案复测不能覆盖首次结果。
- 定义最小实用收益阈值后再看结果。例如增强模块要求不增加高风险错误，且质量改善达到预定幅度，或质量满足预定非劣界时调用/token 明显下降。阈值属于待固定实验方案，不能事后挑最漂亮指标。
- 一旦删掉某机制，应验证它保护的已知反例仍由剩余机制覆盖。安全不变量不能因正常集“看不出差异”而删除。
- 30 案零错建单不代表错误概率为零；小样本只能报告观察结果。不能用此证明生产可靠性。

最终每个保留机制有一张记录：问题 → 最简单基线 → 新机制 → 对照实验 → 增益与代价 → 保留/删除/证据不足。没有可量化增益也没有必要安全反例支撑的增强模块应简化。

## 8. 优化后验收方案

### 8.1 故障与权限矩阵

| 编号 | 故障/输入 | 必须断言的结果 |
| --- | --- | --- |
| F01 | 同请求键、同输入并发 100 次 | 同 run/回执；外部效果最多一次；不同输入复用键返回冲突 |
| F02 | 相同业务动作跨会话、不同请求 ID | 按活动案件去重口径合并或明确拒绝，不绕过业务唯一约束 |
| F03 | 记录操作意图后、网络发送前 kill worker | 可恢复为未派发/待核对，状态不会永久未知 |
| F04 | 外部已建单后丢响应、worker 崩溃 | 根据稳定键核对既有工单，无盲重建 |
| F05 | 外部成功后事务库暂不可写 | 恢复后仍能核对；UI 不错误提示“未执行，可以重复” |
| F06 | Redis 清空派生键或会话 TTL 到期 | 持久业务结果可查；权限不能由缓存缺失而放宽 |
| F07 | A 租约过期、B 接管、A 恢复 | A 的陈旧写被拒绝；单操作不会产生第二个效果 |
| F08 | 读操作前取消、写操作派发后取消 | 前者停止；后者核对结果且清楚报告，不能伪装撤销 |
| F09 | 模型 429/超时/空输出/畸形 JSON | 调用次数与deadline受预算约束，语义失败可诊断 |
| F10 | 恶意工具 metadata、提示注入、越权订单 | 在工具执行前拒绝非法权限，不因提示词放行 |
| F11 | 策略/参数更新后使用旧确认 | 拒绝旧凭证并展示需重新确认的方案 |
| F12 | RAG 更新、worker 缓存不同步、Chroma 中断 | 不把陈旧策略当事实；业务流程按声明降级 |
| F13 | 评测报告混版本、工具先建单后核验 | 比较器/流程断言失败，不能形成合格报告 |
| F14 | schema 升级失败、备份恢复、回滚 | 已有运行结果和幂等键可查；恢复前后业务计数一致 |

测试要验证业务效果与持久状态，不能 mock 被测恢复器/状态机本身。单测可替换模型与网络；租约、事务和进程接管必须增加真实服务与独立进程测试。

### 8.2 性能与可用性目标（候选门槛，尚未验证）

在记录 CPU、内存、Docker 资源、镜像 digest 的隔离主机环境，先使用确定延迟的模型/Provider stub，避免把公网波动当运行时性能。

- 设执行并发 C=8、最大排队 Q=32，模拟 1 秒模型和 100ms 只读工具；这些是测试配置，不是当前容量结论。
- 分别以 1/8/32/100 并发运行 10 分钟，固定请求结构；多用户与同用户热点分开测。
- 在途执行不超过 C，排队不超过 Q；超量请求快速返回明确拒绝，目标 P95 <500ms。
- 注入单个 2 秒慢 Provider 时，健康查询目标 P95 <200ms；事件循环延迟 P99 <100ms。测试机无法满足则先分析基线，不通过事后降低门槛掩盖阻塞。
- 运行完成后无持续增长的任务、连接或内存；与预热稳定值相比 RSS 增幅目标 <20%，同时报告绝对占用和样本。
- worker 被 kill 后，可恢复任务在租约过期加两次轮询周期内开始接管；以租约 5 秒、轮询 1 秒为测试配置时，目标 10 秒内开始恢复。外部结果不可查时不承诺 10 秒内完成交易。
- 已接受任务均进入成功、失败、等待输入、结果待核对等可查询状态；有限实验内无丢任务/重复副作用，保留原始计数。
- 真实模型延迟、语义质量和费用单独测量；不把 stub 结果写进简历当作真实模型端到端性能。

### 8.3 每个里程碑的验收包

包含代码提交、迁移/配置版本、构建 digest、测试命令与结果、故障种子、脱敏逐案报告、指标定义、失败样本、回滚方法和剩余限制。原始日志不应整体提交；发布脱敏报告和校验 hash，注明原始产物位置与保留期限。

## 9. 面试展示如何对应工程能力

当前可以诚实展示的主线：物流状态机决定副作用、明确确认、局部幂等、工具白名单/Schema、失败回执、案件级评测与历史消融。当前适合称“物流异常 Agent 应用，含可靠性与评测工程实践”。

完成 M1–M3 后，建议演示三个证据链：

1. **可靠执行**：发起案件 → 外部工单成功但响应丢失 → kill worker → 新 worker 核对结果 → 返回同一工单。说明保证边界与唯一键。
2. **资源治理**：并发压入请求 → 接入拒绝/排队可见 → 其他用户仍可运行 → 模型预算不超限。展示任务、队列与模型调用指标。
3. **实验驱动减法**：对比规则/LLM/向量或长期记忆的配对报告，解释保留、关闭或待验证的决定，而非只展示框架数量。

完成后再使用“可恢复 Agent 运行时”“工具治理”等描述，并注明实验规模。尚不能声称通用 Agent 平台、真实承运商接入、生产高可用、多租户完全隔离、全链路 exactly-once 或已验证的百万级容量。

底层复用来源继续以 NOTICE 为准；工程贡献应落在自己能够解释、复现并维护的变更上。
