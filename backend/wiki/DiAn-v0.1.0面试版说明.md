# DiAn v0.1.0 面试版说明

冻结日期：2026-11-10

## 项目定位

DiAn 是独立维护的物流异常客服 Agent 项目，面向疑似丢件、签收争议和破损错发场景。项目复用通用客服 Agent 的基础设施，并重新设计物流领域状态机、写操作边界、模拟业务接口、前端案件工作台和案件级验证体系。底层来源和基线 commit 记录在仓库根目录 `NOTICE.md`。

## 本版可展示能力

- 多轮收集订单号、运单号和材料声明，保存案件状态并支持刷新与服务重启后的恢复。
- 通过固定模拟工具核验订单归属、订单与运单关系、物流轨迹及异常规则。
- 只有案件已核验并进入 `awaiting_confirmation`，且用户下一轮明确确认时，才允许创建模拟工单。
- 请求重放、并发确认和重复确认不会为同一案件创建多个工单。
- 查询失败、事实冲突和人工请求进入保守状态，不虚构承运商操作、退款或赔偿结果。
- 订单、物流、工单和证据使用 Provider 接口隔离；当前发行版只包含模拟实现。
- 评测器逐轮检查案件状态、工具轨迹、禁止动作、工单数量、案件号和工单号连续性。

## 指标口径

30/30 表示案件状态、路由角色、工具调用、禁止动作、工单数量和身份连续性等确定性流程断言通过。自然语言回复仍标记为 `pending_human_review`；冻结测试集的双人语义复核尚未完成。当前结果只适用于固定模拟工具世界，不能解释为生产准确率、可用性或 SLA。

## 面试讲解主线

1. 为什么不能让模型直接决定建单：模型负责理解表达，领域状态机负责事实、授权和副作用。
2. 如何防止重复工单：请求回执幂等、案件级稳定身份、数据库唯一约束和 Provider 幂等键共同约束。
3. 如何处理模型失败：明确异常规则可安全接续；只有向量猜测而没有规则依据时，不能启动物流异常案件。
4. 如何证明方案有效：用案件级多轮数据验证状态、工具和副作用，并比较规则、LLM 与向量分支。
5. 为什么还不能上线：真实系统适配、生产身份、文件证据真实性、正式数据库和人工语义复核尚未完成。
