# DiAn 快递鸟 8002 只读接入验收

已按用户提供的账户文档接入 `RequestType=8002` 和 `https://api.kdniao.com/api/dist`。用户确认运单可用于本项目查询后，完成一次独立连通探测与两轮 /chat 联调，共三次外部请求。三次返回均为 Success=true、State=0、空 Traces，当前完成的是鉴权查询、空轨迹处理和归属边界验证，有有效轨迹的实时展示继续待验。

## 接入范围

- `core/kdniao_tracking.py` 实现现有 TrackingProvider 的 query_logistics 接口。按未编码 JSON 加 AppKey 的小写 MD5 十六进制串计算 Base64 签名，通过表单编码提交。请求固定为 8002 网关，Sort=1 请求最新轨迹优先。
- `agents/tracking_tools.py` 提供可选的 query_authorized_tracking，只接收订单号。用户身份来自请求上下文，运单、承运商编码与验证尾号来自服务器本地绑定。
- 工具声明 status_lookup:logistics，仅在 General 角色与物流查询主题下提供相应能力。物流查询能力不会令退款实时查询变为可用。
- 正常 API 启动及工具刷新通过现有注册入口加载该工具。模型评测用的独立编排器继续使用原有独立工具集合。
- /chat 增加可选 tracking_query 结构化字段，包含 success、source、query_performed、queried_at、has_traces 和归一化结果。模型正文与权威查询结果均可核对，旧回执缺少字段时默认为空。

外部查询通过独立只读工具展示，案件核验及模拟工单仍使用既有演示 Provider。本轮尚未将外部轨迹纳入案件责任判断或建单裁决。

同步网络 I/O 使用既有 finish_blocking_call 在线程执行，连接超时 5 秒，其他 HTTPX I/O 超时 10 秒，无自动重试。每个请求最多尝试一次外部物流工具，重复 HTTP client_request_id 复用既有回执。该配置面向本轮小范围查询。

## 当前本机配置

凭据写入被 Git 忽略的 backend/.env，授权绑定写入 backend/data/logistics/kdniao-orders.json。真实商户号、密钥、电话验证信息和运单号均留在本机。公开 .env.example 使用空白占位。

开启配置为 DIAN_TRACKING_PROVIDER=kdniao，并设置 KDNIAO_EBUSINESS_ID、KDNIAO_API_KEY、KDNIAO_ORDER_BINDINGS。模板默认 provider 为 mock。绑定结构示例如下，内容需替换为实际获准查询的数据。

```json
[
  {
    "user_id": "your-test-user",
    "order_id": "LIVE1001",
    "tracking_no": "YOUR_AUTHORIZED_TRACKING_NO",
    "shipper_code": "YOUR_CARRIER_CODE",
    "customer_name": ""
  }
]
```

CustomerName 按账户接口文档填写需要的寄件人或收件人尾号。绑定文件由服务器配置维护。现阶段订单归属来自这个本地清单，尚未对接真实订单管理系统。开发中的测试身份与运单绑定不能替代生产订单授权。

## 实测

独立探测的 HTTP 状态为 200，耗时约 828 毫秒，返回“暂无轨迹信息”。签名和网关能够正常受理请求。

使用实际 ASGI /chat、真实意图与回答模型、Bearer 身份映射进行最终联调。会话 Redis 使用协议模拟器，案件库使用临时 SQLite。

| 场景 | 外部请求次数 | 结果 |
|---|---:|---|
| 已绑定用户查询本地订单 LIVE1001 | 1 | source=kdniao，status=no_tracking，has_traces=false，附查询时间 |
| 同一用户重复同一 client_request_id | 0 | 回复和结构化结果与第一次完全相同 |
| 另一身份在请求体冒用原用户查询 | 0 | 身份取自 Bearer，归属校验未通过，source=local_order_binding，query_performed=false |

三次 HTTP 请求均完成，未生成案件工单。模型调用了真实 query_authorized_tracking，最终已绑定用户回复注明快递鸟来源与查询日期，并说明空轨迹无法决定丢件、运输中或签收。

第一轮 /chat 联调验证一次外部调用，随后补充结构化查询元数据，再完整联调一次。两轮均验证回执复用和归属拒绝。加上独立探测，本轮累计外部请求三次。供应商实际计费与剩余额度以账户后台为准。

## 结果分类与边界

Success=true、Traces=[] 表示接口受理但当前无轨迹，返回 no_tracking。不会回填模拟轨迹或推定物流状态。Success=false、HTTP 异常和超时返回明确查询错误。签收状态仍只表示系统记录。

归属拒绝的结构化字段明确表示未查询外部接口。当前模型在拒绝回复末尾仍有建议补充手机号尾号等无用信息的现象，这些信息不会解除绑定限制，也不能触发额外查询，后续需改进该失败场景的回复。技术边界验证通过，未将该段措辞计为完整语义验收。

本轮使用真实供应商及真实请求，尚未获得可展示的真实轨迹。首轮有轨迹的解析仅通过协议响应样本验证。下一次验收应使用一票可返回有效轨迹的授权运单，检查最新节点、城市、更新时间与用户可见回复。常规测试复用已保存的脱敏响应，真实调用按需进行。

## 验证与复现

三项新增协议测试覆盖签名与表单、越权请求不出站、成功空轨迹、有轨迹解析、供应商拒绝、超时，以及物流能力与退款主题隔离。51 项直接相关测试通过，随后结合物流案件与 API 回归共 85 项通过，有一条原有依赖警告。

```powershell
python -m evaluation.verify_kdniao_chat --output data/kdniao/chat-acceptance.json
python -m pytest -q tests/test_kdniao_tracking.py tests/test_agent_orchestrator.py tests/test_chat_reliability.py tests/test_intent_recognizer.py
```
