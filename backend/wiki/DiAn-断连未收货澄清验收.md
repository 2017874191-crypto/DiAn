# DiAn 断连未收货澄清验收

承接[固定模型故障对照](DiAn-固定模型故障对照验收.md)。基线为 `573846b`。当两个模型阶段同时断连，`DIAN-025` 的含蓄未收货请求在完整三路、LLM＋规则、关闭物流向量三组都返回 503。当前缺口是在信息不足时给用户一条可继续的路径。

## 改动和边界

- 以意图识别器实际失败为触发条件。低置信度、有效的模型输出和禁用模型的纯规则模式沿用各自原路径。识别失败结果跳过意图缓存，让新的请求可以感知服务恢复。
- 当本轮提供唯一订单号、明确表示未收货并询问是否遗失，且当前没有活跃案件、既有明确异常信号或人工请求时，直接询问是核查疑似丢件还是查询进度。普通查件、运费、已收货、否定核查和多订单号等条件排除在这条窄规则之外。
- 澄清返回固定文字，走原有聊天回执与路由记录。该轮不执行回答模型调用，不更新订单上下文，不产生案件或工单。用户补发订单号和明确异常后走原核验流程，建单仍要求上一轮已经完成核验并处于待确认状态。

## 对照和反例

使用实际 `/chat`、本地 SDK 传输故障、Redis 协议替身和临时 SQLite。每组以同一输入在两个模型阶段施加连接故障。基线只在试验进程内移除新的澄清判断，三组业务规则、数据和故障不变。

| 识别配置 | 移除定向澄清 | 启用定向澄清 |
| --- | --- | --- |
| 完整三路 | 503，尝试回答模型 | 200，固定澄清 |
| LLM＋规则 | 503，尝试回答模型 | 200，固定澄清 |
| 完整模式，关闭物流向量 | 503，尝试回答模型 | 200，固定澄清 |

启用后，澄清轮的案件数和工单数均为 0。直接回复“确认建单”，即使模型恢复并把它识别为丢件，也只会得到待补资料状态，工单数仍为 0。故障持续且用户先带单号补发“疑似丢件”，随后明确确认的三轮对照中，案件状态依次为空、`awaiting_confirmation`、`ticket_created`，工单数依次为 0、0、1。回放断言验证订单、物流、策略核验的顺序与确认门槛。

反例验证覆盖普通查件、运费与未收货混合请求、否定未收货、否定核查、已经收货、缺少单号和多个订单号。已有待确认案件的状态保留，健康模型能够继续按原流程处理。失败识别之后，同一文本下次可以重新调用模型，成功识别仍可缓存。

```powershell
python -m pytest -q -s tests/test_logistics_clarification.py
```
