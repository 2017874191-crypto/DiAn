# DiAn 案件关联持久化验收

日期：2026-11-11。目标：修复会话 Redis 状态丢失后，业务数据库中仍有案件和工单、`/logistics/case` 却返回空的缺口。此改动同时作用于原路径与可选 Temporal 路径；没有更换执行引擎或模拟工单提供者。

## 实现与约束

- 业务库增加 `active_cases(user_id, conv_id, case_id, updated_at)`，以 `(user_id, conv_id)` 为唯一键。在保存案件和模拟工单的**同一个 SQLite 事务**中更新当前案件关联。人工复核状态更新也刷新关联。
- 查询通过 `active_cases` 与 `cases` 按案件 ID、用户 ID、会话 ID 同时连接，返回案件的最小只读视图。即使 Redis 携带错误或旧的案件指针，也以业务库当前关联为准，不跨用户或会话读取。
- `/chat` 读取会话上下文后，以业务库当前案件恢复缺失的物流标识、案件状态以及当前订单/运单实体。短消息“确认建单”在 Redis 状态过期后仍能继续原案件，但领域代码仍要求前一状态可确认；恢复标识本身不授予写操作权限。
- 对升级前的 `cases` 表，初始化时仅为尚无当前关联的会话补写一条：取 `payload.updated_at` 最新者，同时间以行号打破平局。迁移是历史数据的最佳努力推断；缺少可信时间或损坏数据时需人工核查，不把“最近”当成用户真实选择的证明。后续每次切换案件均显式写入，不再靠时间推断。

## 验收方法与结果

从 `backend` 目录运行 `python -m pytest tests/test_logistics_api.py tests/test_logistics_cases.py tests/test_temporal_logistics.py -q`。目标测试覆盖：

| 场景 | 期望 |
| --- | --- |
| 清除 Redis 案件状态后读取原会话 | 从业务库返回同一案件 |
| 清除状态后继续确认建单 | 恢复案件关联，仍通过原领域确认门槛 |
| 同一会话切换订单或案件 | 当前关联指向新案件，旧案件仍按原归属保留 |
| 其他用户、其他会话、伪造旧指针 | 无法读取或接管原案件 |
| 从升级前只有 `cases` 的数据库启动 | 对原会话回填最近案件关联，重启后保持一致 |
| 原路径与 Temporal 路径重跑固定数据集 | 8 个案件、14 个用户轮次，状态及工单数逐轮一致；会话指针丢失后两组均可回查 |

本次对照原始记录见 [JSON](../evaluation/temporal_comparison.json)，实验条件及延迟见[主链路对照报告](DiAn-Temporal主链路对照实验报告.md)。物流相关测试 35 项通过；完整测试集 210 项通过、1 条测试工具弃用警告（Windows Python 3.11.9）。迁移测试使用不同时区的时间戳验证实际时间排序。本次测试以受控会话替身清空状态模拟 Redis 过期，尚未测真实 Redis TTL、断线或多实例竞争；项目目标运行环境仍需 Python 3.12 容器复验。

## 能力边界与下一步

案件回查与业务状态恢复已经持久化；聊天历史、Redis 请求回执和模型上下文不因此变成永久数据。`active_cases` 当前使用 SQLite，适合现有演示环境；多实例高并发与真实外部系统接入仍需明确数据库部署和事务边界。下一步按复用方案验证独立 HTTP 工单服务、Operation 业务账本、稳定幂等键、结果未知时核对，以及确认与案件版本、参数绑定。Temporal 保持默认关闭，直至这些故障和成本门槛通过。
