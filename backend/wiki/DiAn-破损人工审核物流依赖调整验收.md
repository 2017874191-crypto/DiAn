# DiAn 破损人工审核物流依赖调整验收

日期：2026-11-22。改动前基线：`0cd414aa9fb9e0956f6e043c54e479f84867f83a`。

## 业务决定

破损错发分支的动作是提交模拟人工审核工单，不是批准售后或承运商理赔。该动作保留订单归属、材料提交声明、下一轮明确确认、同订单同问题去重及副作用结果核对；物流轨迹不再作为统一前置条件。

这一决定与既有 `policies.json` 的“记录用户已提供材料的声明后，可提交人工审核；不自动判责赔偿”一致。政策文本及版本未修改；此次修复的是实现额外施加的物流查询依赖，不更改用户确认的动作或赔付资格。已经派发、结果未知或挂起的工单仍走原核对/人工处理路径，不能因本次简化重新派发。

参考的是业务阶段划分：[Shopify](https://shopify.dev/docs/api/admin-graphql/2026-01/mutations/returnRequest)将申请与批准分开；[Medusa](https://docs.medusajs.com/user-guide/orders/claims)将缺陷商品Claim、退货及资金处理分别管理。二者不能证明所有业务都无需物流，DiAn的取舍取决于当前仅提交人工审核的动作边界。本轮未引入这些平台或复制其业务代码。

## 实现与能力边界

| 分支 | 订单归属 | 物流读取 | 提交动作 |
| --- | --- | --- | --- |
| 破损错发 | 必须通过；提交了运单仍须与订单匹配 | 当前提交路径不调用 | 材料声明记录后展示事项，下一轮明确确认，再创建模拟人工审核工单 |
| 疑似丢件 | 必须通过 | 仍必须成功 | 查询失败仍保存待人工核查，不推定丢件 |
| 签收争议 | 必须通过 | 仍必须成功，并保留签收事实冲突处理 | 不能因本次修改跳过签收核验 |

- `core/logistics.py` 仅对 `logistics_damaged` 跳过轨迹读取；订单提供者返回可信订单身份即可，不强求提供运单字段。用户提供运单时的匹配检查仍由原订单Provider负责。
- 案件持久化 `facts={"query_performed":false,"reason":"not_required_for_damage_review"}`，不伪造成功查询、轨迹或签收事实，也不制造不存在的工具调用记录。
- 待确认回复说明仅核验归属、记录声明、未查物流和未验证图片；成功及重复回执补充未验证图片、未判定责任。案件卡片的下一步提示与该边界一致。
- 同步更新角色规范与README。没有增加模型判断层、可选查询后台任务、数据库表或新的执行框架。

图片上传、真实性审核、赔付批准和真实退款仍未实现。自然语言确认仍沿用当前固定表达解析；材料声明仍沿用原解析器，语序覆盖不足的问题不在本轮顺带修复。不能声称上批外部验证草稿已全部通过。

## 验证方法与结果

先将物流Provider替换为“一旦调用即报错”，保留真实领域状态机与SQLite。修改前该破损回归在首次申报时失败，暴露实际硬依赖；另外三项归属/其他类型反例通过。修改后验证：

| 检查 | 需要观察的结果 |
| --- | --- |
| 破损申报且无物流能力、订单无运单字段 | 可以进入待材料/待确认，不触发物流调用 |
| 缺材料或否认上传，同时发送确认 | 不建单 |
| 首次声明材料时同时发送确认 | 先展示事项并等待下一轮，不在同轮跳过确认 |
| 下一轮明确确认、重启后重试、另会话重复申请 | 创建后返回原工单，另一会话同事项被去重，工单总数1 |
| 三类案件的非本人订单 | 归属失败，不读取物流、不建单 |
| 丢件和签收争议的物流能力失败 | 仍停在待人工处理，不建单 |
| 实际 `/chat` 接入独立模拟HTTP工单，远端提交成功后丢响应 | 待确认→结果未知→核对为已建单，远端工单总数1；破损全程物流调用0 |

HTTP验证复用已有测试，仅增加破损参数；模型意图识别和会话存储使用测试替身，领域代码、API与跨进程模拟HTTP工单实际执行。因此它证明受控工程路径，不证明模型语义泛化、真实Redis部署或供应商生产行为。

运行命令：

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_logistics_cases.py tests/test_logistics_api.py tests/test_logistics_http_operation.py tests/test_logistics_eval_runner.py
```

本机结果：65项通过，耗时62.07秒，1项既有依赖弃用警告。新增测试实例合计5项，其他为原回归；没有扩展故障矩阵。模型、快递鸟和真实工单系统调用均为0。
