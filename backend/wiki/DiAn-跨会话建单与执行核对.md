# DiAn 跨会话建单与执行核对

## 建单规则

同一用户、同一核验后的订单、同一异常类型，在同一案件库中最多拥有一张未结案工单或一个未决建单操作。通过运单号进入的案件先归一到订单号。会话仍有各自的案件和运行记录，冲突会话只收到 `ticket_already_open` 提示。不同订单和不同问题类型分别处理。

确认时，SQLite 写事务先检查该范围内的工单与 Operation，再创建同库工单或持久化独立 HTTP 工单的操作意图。远端 I/O 发生在事务提交之后。响应丢失、结果未知及人工挂起都会占用原范围。历史工单也参与检查，既有重复记录保留供人工核对。

管理员在确认工单已经处理完毕后，可以调用 `POST /logistics/cases/{case_id}/close`，传入案件所属的 `user_id`、`conv_id` 和 10–500 字的 `reason`。系统记录结案时间、操作者和原因。原工单和记录保留，新的申请需要重新核验和确认。操作结果未决时，接口返回 409。结案只改变 DiAn 内的案件状态。

## 回放与核对

回放器验证实际建单轨迹的前置条件。上一轮需要是同案件的待确认状态，本轮需要收到明确确认，且订单查询、物流查询、规则核验须依次成功。核对已有 Operation 使用独立轨迹名称。回放数据集中多个用例复用模拟订单，独立部署上的回放器会在用例结束时结案以隔离样本。开启鉴权的回放可以用 `--token` 发送模拟用户请求，并用 `--admin-token` 读取轨迹和结案。

独立 HTTP 模式复用原有 GET 核对器和管理员挂起入口。未决年龄从 Operation 首次保存开始计算。旧数据库用已有的更新时间补齐初始年龄。核对器按最近更新时间选择扫描对象，继续按原键查询远端结果。无权威结果时保留未决记录，管理员可核对和挂起。

`DIAN_TICKET_RECONCILE_ALERT_AFTER` 默认 300 秒。核对器输出未决数、最老年龄、超时数和挂起数，并在超时出现时记录警告。HTTP 模式的 `/metrics` 提供同名的 `dian_ticket_reconcile_*` 指标，Prometheus 持续观测到超时两分钟后触发 `DiAnTicketReconciliationOverdue`。启用 API 鉴权时，Prometheus 抓取需配置管理员凭据。可在 Prometheus 查看告警状态。

## 验收范围

- 并发确认使用同一订单的订单号和运单号入口，检查只创建一张工单。结案后重新核验、确认可创建另一张工单。
- 独立 HTTP 工单响应丢失时，另一个已到待确认状态的会话无法创建第二张工单。后台核对能取回原工单。
- 将建单放到核验前，再把物流核验标为失败。即使工具集合和最终工单数符合预期，回放仍应失败。
- 检查挂起前后的未决年龄、超时和挂起指标，并验证普通用户和未决案件的结案请求受限。

本机消融使用两个独立的临时 SQLite 文件。两组均用同一模拟用户、订单 DEMO1001 和丢件类型，在两个会话分别核验后并发确认。仅将 `_has_other_open_ticket` 替换为始终返回 `False` 时，两轮均为 `ticket_created`，数据库有两张工单。恢复真实范围检查后，一轮为 `ticket_created`、一轮为 `ticket_already_open`，数据库有一张工单。

本机后端全量 235 项通过，前端 17 项通过，前端生产构建和 `promtool check config` 通过。通过 FastAPI 实际路由连续回放 DIAN-014 和 DIAN-016，两案复用同一模拟订单，分别完成核验、确认、建单和管理员结案。该回放使用内存会话替身和规则识别。另一个用例 DIAN-013 在纯规则模式下未识别为物流问题，因此该结果仅覆盖选定的执行流程。

这些验收覆盖共享 SQLite 文件、独立模拟工单和本机部署。后台每轮至多扫描 100 条，若最早一批持续无法收敛，后续记录可能排在扫描批次之外，积压指标仍覆盖全部未决记录。真实工单系统的结案、查询权威性和多机部署需要按其接口和存储重新验证。
