# DiAn 错发与签收争议语义边界优化验收

日期：2026-11-19。基线产品版本 `f7571ce`，候选版本 `47b2d68`。

本轮只在已有意图模型提示词中增加 10 行类别定义与 3 条成对示例，说明收到商品但商品、型号、颜色不符属于现有 `logistics_damaged`（含错发），签收记录与实际未收件的冲突属于 `logistics_dispute`。没有新增意图、模型步骤、Agent、融合权重、确定性关键词、确认门槛或权限规则。

本轮证据支持保留这一小改动用于现有演示业务的主题识别，同时保留目标判断与政策回答的缺口。不能声称所有语义问题已解决。

## 事先固定的配对对照

[执行协议](../evaluation/reviews/dian_logistics_v1/intent-boundary-protocol.json)与候选一起提交后，才开始模型调用：5 条上轮已曝光的错发失败，加 7 条开发边界请求，共 12 条，5 轮配对、每组 60 次。旧代码从已提交的 Git 版本加载，候选使用当前识别器；两组均运行实际 `recognize`、同一模型 `deepseek-v4-pro`、同一配置和 SDK 零重试。物流向量关闭，其他意图可用本地 n-gram。

每对交替先后顺序，最多同时运行 2 对，每次创建新识别器，避免结果缓存代替模型调用。意图融合和规则代码相同，主要变量是新增的提示词段落，源码哈希和逐次推理、token、耗时均保留在[原始配对记录](../evaluation/intent_boundary_paired.json)。

五条错发请求重点核验类型，其目标允许事先声明的咨询、申请或澄清；七条边界请求另有明确目标期望。全部标签由 Codex 制定，独立人工复核为 0。这是已曝光开发与回归样本，重复次数不能当成新增独立问题数，也不构成泛化准确率。

### 目标退化不能被总分掩盖

DIAN-010-goal 的“发错货了，应该怎么处理”事先目标为 `uncertain`。旧版 5/5 为 `uncertain`，候选 5/5 为 `policy_question`，虽然类别已修正。这是实际观察到的目标行为变化，不能因为任务目标文字本身未修改，就宣称目标行为完全不变。

预先门槛约束错发类型改善、控制组联合命中总数、不增加未请求的办理目标、调用与模型错误，自动检查全部通过。但该联合总数门槛不能保证每个目标无退化。这里单列这个反例，不改期望或阈值来消除失败，不在同一组上继续调参刷分。

### 提示词有实际代价

旧版提供商报告非缓存输入 2,689、缓存读取输入 43,776、输出 2,973；候选分别为 11,537、48,128、3,064。合计输入每次意图调用增加 220 token（按此次提供商报告口径，缓存创建均为 0），没有节省调用数。P95 差约 92ms 不足以证明变快，时间邻近配对与缓存也不能消除供应商运行波动。

保留的理由是少量提示信息修正了明确业务类别错误，且无需新增模型判断层；不是把更长提示词包装成免费优化。

### 原五案的实际表现

- DIAN-007、011 进入正确的待材料流程。

## 仍未解决的内容与下一步

[逐轮语义复核](../evaluation/reviews/dian_logistics_v1/codex-boundary-observed-review.csv)保留 28 轮原文：21 轮在演示约定下相符，1 轮可接受的材料咨询替代回答，1 轮需裁定目标，1 轮有目标及政策问题，4 轮指引不足或缺政策依据。来源仍为 Codex 辅助检查，不能替代独立人工金标。

配送时间入口提示依然偏泛；取消寄送仍补充资料未支持的拦截/拒收规则。改址回复本轮有检索并引用发货前联系客服，但仍补充未获资料支持的发货后判断。它们都未被本轮主题定义解决。

下一小项按原优化计划收敛目标与回答依据：先明确“咨询怎么处理”和“申请处理”的可接受行为，再验证规则咨询能否使用已有知识工具、缺政策时能否直接说明。保留单次意图识别与现有材料、确认、授权规则，不靠再加一层 Judge、扩大硬关键词或强制所有具体订单问题建案解决。

正式泛化验证另用未参与调参的问题与独立复核。真实有轨迹接口验收仍需客户验证尾号，Temporal 与真实写操作继续按既有边界暂缓。
