> 本文档是当前版本的开发基线，不是产品宣传稿。它区分“已经由代码/测试验证的能力”“仓库文档中声明但尚未完整验证的能力”和“下一阶段计划”，后续需求、代码评审和验收均以本文档为准。

## 1. 文档依据与项目现状

本次梳理依据以下材料：

- 远程仓库：<https://github.com/2017874191-crypto/DiAn>
- 当前工作区中的 EchoMind Python 后端代码、测试、配置和 wiki

DiAn 仓库包含 `backend/` 和 `frontend/` 两个部分，定位为“物流异常协同台”。项目复用通用客服 Agent 的基础设施，并独立维护物流领域模型、前端案件工作台、评测数据和验收证据。底层来源与基线版本统一记录在仓库根目录 `NOTICE.md`。

截至当前版本，已经完成的主要方向是：

1. 在 EchoMind 原有多 Agent 客服后端上增加物流异常领域。
2. 支持疑似丢件、签收争议、破损错发三类案件。
3. 增加案件状态、信息补全、事实核验、用户确认、模拟工单和幂等处理。
4. 增加前端案件卡片所需的案件快照接口。
5. 增加带来源、许可和场景约束的案件级评测数据集。
6. 增加重启、并发、重复请求、权限隔离和错误降级相关回归测试。

## 2. 项目目的

### 2.1 核心目的

DiAn 的目的不是让大模型自由决定物流业务动作，而是把客服对话转化为一条可审计的案件处理流程：

> 收集必要信息 → 查询受控事实 → 判断当前状态 → 在明确确认后执行下一步 → 保存案件和轨迹 → 向用户返回可解释结果。

项目重点解决四类工程问题：

- 多轮对话中如何持续保存订单、运单、证据和案件状态。
- 当用户的自然语言不完整、含糊或与物流事实冲突时，如何先补信息或转人工，而不是猜测。
- 创建工单等写操作如何做到确认、幂等、可追踪，避免重复建单。
- 如何把模型能力限制在意图识别和语言表达，把业务事实和状态迁移交给确定性代码。

### 2.2 目标用户与使用场景

当前主要面向：

- 客服人员：查看案件状态、已核验信息和待补材料。
- 终端用户：通过多轮对话提交订单信息、补充材料并确认处理。
- 开发和测试人员：验证 Agent 路由、状态机、工具调用和异常恢复。
- 后续业务系统：通过稳定接口接入真实订单、物流、工单和证据服务。

首版演示数据使用 `DEMO1001`—`DEMO1004`，分别覆盖疑似丢件、签收争议、破损错发和查询超时。它们是模拟工具世界，不代表真实承运商数据或真实赔付规则。

## 3. 非目标与能力边界

以下内容当前明确不属于已完成能力：

| 事项 | 当前边界 |
| --- | --- |
| 真实物流查询 | 当前为模拟物流服务；不能据此声称已接入承运商。 |
| 真实工单 | 当前只写入模拟 SQLite 工单；不等于已提交企业工单系统。 |
| 真实赔付、退款 | 不执行赔偿、退款或资金操作。 |
| 证据核验 | 目前只记录“用户声明已提供材料”，不验证图片、文件内容或真实性。 |
| 身份鉴权 | development 模式下的 `user_id` 隔离不能替代生产 Token、租户和权限系统。 |
| 法律/保险结论 | 不判断责任归属、赔付金额或承运商法律义务。 |
| 自动化全场景客服 | 只承诺当前定义的物流异常场景和原 EchoMind 的通用、技术、账单、转人工路径。 |
| 生产 SLA | 当前测试和联调结果不能推出生产准确率、吞吐量、可用性或延迟承诺。 |

一个重要边界是：物流流程不是“模型自主规划的多 Agent 协作”。模型可以参与意图识别、角色响应和语言生成，但物流核验顺序、确认要求、写操作和状态迁移必须由领域代码控制。

## 4. 设计原则与工程约束

用户提供的原则图片被解释为本项目的工程约束，而不是仓库中的具体业务需求：

> 从第一性原理重新分析，对当前方案做对抗性审查；核心机制必须通过消融实验验证；方案遵循奥卡姆剃刀，代码保持高内聚、低耦合。

落到 DiAn 的具体要求如下：

### 4.1 第一性原理

每个业务动作先回答三个问题：

1. 当前动作需要哪些事实？
2. 哪些事实已经可靠获得，哪些只是用户陈述？
3. 这个动作是否会产生不可逆或外部副作用？

因此，建单不能仅由模型输出“建议建单”触发，必须同时满足案件状态、必要字段、工具核验结果和用户确认条件。

### 4.2 对抗性审查

每个物流场景至少要审查以下反例：

- 缺订单号、订单与运单不匹配、用户无权访问订单。
- 用户在否定句中提到“转人工”，不能被误识别为明确转人工。
- 模型把物流问题误分到其他意图，或把人工请求误分为物流问题。
- 用户重复发送确认、客户端重试、并发提交确认。
- 服务重启后再次发送短消息，不能丢失案件或重复建单。
- 物流查询超时或返回冲突，不能伪造查询成功或直接认定责任。
- 新订单进入同一会话后，不能沿用旧案件或旧工单。

### 4.3 核心机制必须可验证

“模型回答得通顺”不能作为核心机制的验收标准。优先通过确定性断言验证：案件状态、工单数量、工单 ID、工具调用、权限结果、轨迹事件和重启恢复。模型质量另行通过案件级评测、人工复核和 Judge 评测验证。

### 4.4 简化与解耦

- 物流状态迁移集中在 `core/logistics.py`，不散落在提示词和 HTTP 层。
- Agent 只通过受控工具访问物流领域服务，不能直接修改数据库。
- 案件快照与内部存储结构分离，前端不依赖 SQLite 表结构。
- 知识库、Skills、Agent 路由和物流领域服务保持独立，减少一个领域改动对其他领域的影响。
- 能用明确状态和规则解决的问题，不引入额外 Agent 或复杂编排。

## 5. 当前系统架构

```text
前端 / HTTP 客户端
        |
        v
FastAPI /chat
  鉴权、会话锁、幂等回执、上下文读取
        |
        v
IntentRecognizer
  LLM + Embedding + Pattern
        |
        v
AgentOrchestrator
  通用 / 技术 / 账单 / 物流 / 转人工
        |
        +--> LogisticsAgent
        |      |
        |      +--> LogisticsService
        |              SQLite 案件与模拟工单
        |              模拟订单、轨迹、规则
        |
        +--> 其他 Agent
        |      +--> Skills
        |      +--> RAG / MCP / 角色工具
        |
        v
Redis：会话消息、摘要、业务状态、回执、轨迹

        |
        v

```

当前主要入口：

| 入口 | 用途 |
| --- | --- |
| `POST /chat` | 统一对话入口，返回路由、状态、工具使用和案件快照。 |
| `GET /logistics/case` | 按用户和会话读取当前案件快照。 |
| `GET /trace/tool/{request_id}` | 查看单次请求的工具轨迹。 |
| `GET /health` | 检查服务基础健康状态，不验证模型额度。 |
| `POST /eval/run` | 原有意图/对话评测入口；案件级数据集尚未完整接入。 |
| `GET /monitor`、`GET /metrics` | 查看运行统计和 Prometheus 指标。 |

## 6. 物流案件状态模型

当前状态以领域代码为准，典型状态包括：

```text
awaiting_info -> verifying -> awaiting_confirmation -> ticket_created
                    |                   |
                    v                   v
                manual_review       manual_review
```

破损错发多一个举证阶段：

```text
awaiting_info -> awaiting_evidence -> awaiting_confirmation -> ticket_created
```

关键规则：

- 疑似丢件：先核验订单与物流事实，再等待用户确认，确认后最多创建一个模拟工单。
- 签收争议：用户称未收到而模拟轨迹显示已签收时，只能在核验、展示核查方案和用户下一轮明确确认后创建模拟争议工单；不认定责任。若轨迹尚未签收却提出签收争议，则进入 `manual_review`。
- 确认门槛：首次只说“确认建单”不能建单；必须先在同一案件内核验成功并进入 `awaiting_confirmation`，且规则版本一致。
- 破损错发：必须先进入 `awaiting_evidence`；用户直接说“确认建单”不能跳过材料声明。
- 查询超时：保留案件并转人工，不伪造查询结果，不创建不必要工单。
- 新订单：同一会话切换订单时产生独立案件，不继承旧案件工单。
- 明确转人工：优先级高于模型对物流意图的误判；否定表达不能触发强制转人工。
- 并发确认或重试：通过请求幂等和案件/工单约束，保证同一案件不重复建单。

## 8. 关键取舍

| 取舍 | 选择 | 原因 | 代价 |
| --- | --- | --- | --- |
| 模型自由规划 vs 确定性流程 | 物流流程由代码控制 | 降低误建单、越权和状态跳跃风险 | 新场景需要开发状态和规则，灵活性较低 |
| SQLite vs 独立业务数据库 | 当前使用 SQLite | 演示、测试、重启恢复成本低 | 不适合作为多副本生产工单库 |
| 用户声明证据 vs 文件验证 | 先记录声明 | 先打通案件状态和前后端流程 | 不能证明材料真实性，不能用于真实赔付 |
| 模拟工具 vs 直接接真实系统 | 先用固定工具世界 | 可重复测试，避免联调受外部系统影响 | 不能代表真实承运商行为和 SLA |
| 单 Agent 物流路径 vs 复杂多 Agent | 物流由专用 Agent + 领域工具完成 | 物流核心是状态和事实，不是角色竞争 | 暂不覆盖复杂跨部门协作 |
| 案件级数据集 vs 仅字符串断言 | 保存状态、工具、副作用和来源 | 能验证流程和回归原因 | 需要额外 runner、人工金标和评测成本 |

## 9. 下一步开发计划

建议按“先可测、再可接、后生产化”的顺序推进。

### P0：把当前领域成果固化为可重复基线

1. 补齐并锁定开发环境依赖，确保 `pytest` 可直接收集物流测试。
2. 将案件级数据集接入一个独立的 `logistics_eval_runner`：逐案件回放多轮消息，比较案件状态、工具调用、禁止动作、工单数量和幂等结果。
3. 为 runner 增加报告格式：按场景族统计，区分流程通过、语义通过、工具失败、数据失败和环境失败。
4. 对 `test` 集执行人工双人复核，记录金标、分歧和一致性；调参后将暴露用例降为回归集，并重新冻结测试集。
5. 将领域实现整理为清晰提交，明确基线 commit、变更范围和迁移说明。

验收标准：在干净环境中可以一条命令完成数据集验证、物流单测、API 契约测试和案件级回放；报告不会把模型调用失败或环境缺依赖算成业务正确。

### P0.5：规则对齐与消融实验（真实系统接入前）

1. 以领域状态机为唯一写操作裁决点；只有同一案件已经完成核验、进入 `awaiting_confirmation`，且用户下一轮明确确认，才允许创建模拟工单。签收争议按“已签收但未收到可提交核查；轨迹未签收与争议描述冲突则人工复核”执行。
2. 在案件回放中断言重启、重放前后的案件号和工单号相同；统计意外建单，而不只比较期望状态。
3. 使用同一开发集、同一固定模拟工具世界、同一代码镜像、独立数据库，依次比较 `rules_only`（规则＋状态机）、`llm_rules`（LLM＋规则＋状态机）、`full`（LLM＋本地向量匹配＋规则＋状态机）。三组均保留领域规则和写操作约束，差别仅在意图识别分支。`rules_only` 的未命中请求直接澄清，不能落到其他模型客服。
4. 对比流程通过率、意外建单、请求时延、模型调用数和服务方报告的 token；缺少统一价格时不推算货币费用。流程通过不等于回复语义通过，测试集须在人工复核和冻结后再使用。

验收记录见 `wiki/DiAn-P2规则与消融验收记录.md`。若 `full` 未比 `llm_rules` 提高案件流程通过率，应优先评估关闭物流路径的向量分支；这只是开发集上的架构取舍，不代表生产准确率。

后续故障追踪发现：意图模型超时后，低置信度向量曾把运费咨询误建为物流异常案件。已禁止“模型失败＋仅向量识别异常”启动案件，并增加独立的物流向量开关；同镜像两组开发集回放均为 30/30、零意外工单。具体证据与尚待完成的人工复核见 `wiki/DiAn-P3故障追踪与物流向量开关验收记录.md`。

### P1：接入真实业务系统，但保留模拟适配器

1. 抽象 `OrderProvider`、`TrackingProvider`、`TicketProvider`、`EvidenceProvider` 接口。
2. 保留当前 mock provider 作为开发和回归实现。
3. 新增真实系统 adapter，统一超时、鉴权、限流、错误码、重试和脱敏。
4. 外部写操作必须支持幂等键、结果查询和“结果未知”状态，不能只依赖本地重复请求判断。
5. 将 SQLite 的案件/工单表迁移为正式数据库模型，并设计唯一约束、索引和迁移脚本。

验收标准：真实查询失败、超时、部分成功和写操作结果未知均有明确状态；模拟环境回归不受真实系统影响。

### P1：补齐证据链与生产身份

1. 文件上传改为对象存储引用，不把原文件直接塞进会话消息。
2. 保存文件哈希、上传者、时间、类型、大小和病毒扫描结果。
3. 增加图片/文件真实性检查或人工审核状态；未审核材料不能驱动赔付结论。
4. 启用生产 Token、租户/用户身份映射、案件级访问控制和审计日志。
5. 明确个人信息、订单信息、证据文件和日志的保留、删除、脱敏策略。

### P2：前端案件工作台完善

1. 展示案件状态、待补字段、核验事实、待用户确认、证据状态和工单状态。
2. 支持刷新后恢复当前案件；补齐历史案件列表和按用户/会话查询。
3. 将用户可见状态和客服内部状态分离，避免把内部错误码或模型轨迹直接暴露给用户。
4. 为“转人工”“待举证”“查询超时”“工单已创建”设计明确的交互和人工接管入口。

### P2：性能、可靠性和上线准备

1. 进行真实并发压测，覆盖同会话串行、跨会话并发、并发确认和外部接口超时。
2. 明确 Redis、案件数据库、ChromaDB 和对象存储的备份/恢复方案。
3. 增加分布式锁、消息队列或任务编排的容量边界验证。
4. 增加告警：重复建单、案件卡死、外部查询超时、证据处理失败、模型输出截断、鉴权失败突增。
5. 建立灰度、回滚和数据迁移方案。

## 10. 开发约定

### 10.1 新增场景的最小交付物

任何新增物流场景必须同时提交：

- 场景定义和不处理范围。
- 状态图或状态迁移表。
- 必需字段、事实来源和用户确认条件。
- 工具输入输出契约及错误处理。
- 至少一个正常路径、一个缺字段路径、一个冲突/超时路径、一个重复请求路径。
- 单元测试、API 契约测试和案件级回放用例。
- 前端展示字段和用户可见文案。
- 变更说明、数据迁移说明和回滚方式。

### 10.2 代码边界

- HTTP 层负责鉴权、参数校验、会话编排和响应映射，不实现物流业务规则。
- Agent 层负责把请求交给合适角色，不直接绕过领域服务执行写操作。
- `core/logistics.py` 负责案件状态、事实核验、确认和工单幂等。
- 配置文件负责模拟世界、政策和知识内容，不把密钥或用户数据提交到仓库。
- 测试必须优先断言业务状态和副作用数量，再断言自然语言表述。

### 10.3 不允许的实现方式

- 不能仅通过 prompt 要求模型“不要重复建单”来保证幂等。
- 不能把查询超时包装成“已查到”或编造物流事实。
- 不能把用户说“我已提供材料”当成已验证的文件证据。
- 不能用业务字段拼接字符串作为唯一身份而不处理碰撞和跨租户问题。
- 不能把当前模拟数据、联调结果或小规模评测分数宣传成生产准确率和 SLA。

## 11. 结论

当前 DiAn 已经完成从 EchoMind 通用客服框架到物流异常案件原型的关键一步：有领域服务、有案件状态、有确认和幂等、有联调证据，也有案件级数据集。它现在最适合继续做“可重复验证的业务原型”，而不是直接接入真实赔付或把模型权限扩大到生产写操作。

当前案件级评测 runner、隔离验收环境和 provider 接口已具备；真实 adapter、生产身份、证据真实性和测试集人工复核仍是后续工作。下一阶段以 P0.5 消融结果决定物流意图识别配置，再完成金标复核和压力边界验证，随后才设计真实订单、物流、工单及证据系统接入，保持核心流程高内聚、低耦合、可回滚。
